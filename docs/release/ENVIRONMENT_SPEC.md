and its protection rules. GitHub can create a missing environment implicitly,
without protections, when a job references it. Keeping this workflow unmerged
and dispatch-only is the build boundary; do not test it by dispatching it.

| Setting | Required value |
|---|---|
| Environment name | `production_environment` from the single settings block below; initial value `production` |
| Required reviewer | Kevin, currently `kaywhy331` |
| Prevent self-review | OFF until A1 supplies separate identities; all current main actors are `kaywhy331` |

| Environment secret names | `RENDER_API_KEY` only |
| GitHub repository token | Built-in `GITHUB_TOKEN`; no stored personal token |

Database owner/runtime/backup credentials, backup encryption keys and object
storage credentials stay inside the reviewed Render operator services. They are
not GitHub secrets for this workflow. Do not copy secret values into either JSON
variable, a command definition, an approval record, the ledger or a release record.

W1-1 must protect the main, releaser, production-tag and ledger refs. Kevin alone
cuts the reviewed releaser tags; candidate contributors cannot change the code
in the credential-bearing job. The dedicated ledger ref has one logical writer:
the release job. Future recovery workflows use the same concurrency setting,
and must not gain another ledger writer without a reviewed amendment.
The GitHub contents permission is repository-wide; these scripts are not a
replacement for the W1-1 ref protections. A1 and rehearsal h remain go-live gates.

## One settings source

Kevin creates repository variable `RELEASE_SETTINGS_JSON` from this block.
These are the only production defaults; scripts and YAML have no fallback
for missing required settings. Replace each null with a reviewed value from
the deployment inventory or the reviewed job catalog. Service names are read
from the candidate's bound `render.yaml`, never copied into the workflow.

```json
{
  "main_branch": "main",
  "releaser_prefix": "releaser-",
  "production_environment": "production",
  "production_tag_prefix": "prod-",
  "record_branch_prefix": "docs/release-",
  "record_directory": "docs/release",
  "ledger_branch": "release-ledger",
  "ledger_file": "ledger.jsonl",
  "ledger_bootstrap_run": null,
  "concurrency_group": "production-release-and-recovery",
  "render_api_url": "https://api.render.com/v1/",
  "render_owner_id": null,
  "site_url": null,
  "services": { "web": null, "worker": null },
  "health_paths": ["/api/health/ready", "/api/health/live"],
  "request_timeout_ms": 30000,
  "operation_timeout_ms": 1200000,
  "poll_interval_ms": 10000,
  "receipt_prefix": "JITM_RELEASE_RECEIPT:",
  "jobs": {}
}
```

`ledger_branch` is stored as `refs/heads/<ledger_branch>` and must differ from
`main_branch`. For the first run only, Kevin sets `ledger_bootstrap_run` to
that exact GitHub run ID before approving its environment gate. This permits
the first ledger append to create the ref. Remove that value once the ref exists;
only `ledger_bootstrap_run` is excluded from the settings digest, so clearing it
does not invalidate publication. All other settings stay bound.
A missing ledger on any other run fails closed. Never delete or rebuild the
ledger to clear a hold. Non-force ref updates reject concurrent sibling commits;
losing writers stop without issuing the associated provider request.

The concurrency group comes directly from this one variable in workflow-level
`concurrency`; `cancel-in-progress` is false. Recovery must use this same value.
Do not change it while a release or recovery run is pending or active.

## Candidate approval

Kevin creates repository variable `RELEASE_APPROVAL_JSON` for the exact release
and checks it when approving the environment. It contains:

| Field | Required content |
|---|---|
| `candidate` | The five-field record generated by `candidate.mjs`: `candidate_sha`, `approved_main_sha`, `lockfile_sha256`, `render_yaml_sha256`, `migrations_sha256` |
| `release_name`, `migration_job` | Exact dispatch values; migration is `none` or a reviewed job key |
| `reviewed_jobs_sha256` | SHA-256 of `JSON.stringify(settings.jobs)` after parsing the settings; includes every command, service and review reference |
| `review_ref`, `pull_requests` | Recorded review/authority reference and nonempty list of reviewed merged PRs |
| `previous_sha`, `previous_tag` | Previous production candidate and tag, confirmed in preflight |
| `tier3` | `{ "passed": true, "reference": "recorded local candidate-versus-previous-build evidence" }` |
| `dependencies`, `changes`, `rollback` | Reviewed record text, including areas/commits and what older code ignores |
| `owner_followups`, `not_run`, `carried_followups` | Record text, including still-open follow-ups from the previous release |
| `ledger_resolution_sha256` | Only for E3: digest of the exact `ledger_resolution` input string containing Kevin's recorded decision |

Generate the binding from a fetched checkout using:

```sh
node scripts/release/candidate.mjs bind <full-candidate-sha> <current-main-sha> candidate.json
```

The candidate must be an ancestor of the approved main head. After dispatch,
main may fast-forward from that approved head while the same candidate proceeds.
A rewritten main that no longer contains the approved head is refused, even if
it still contains the candidate. A new candidate always needs its own approval.
The candidate binding hashes raw lockfile and blueprint bytes and a sorted list
of every migration file path and content digest. No candidate scripts run to
calculate the binding. Each provider request re-reads main and recomputes it.
The release gate also binds the exact approval string and parsed settings,
excluding only `ledger_bootstrap_run`; other changes between release and publish
are refused. Approval text is public-safe record material.

## Reviewed one-off job settings and receipt contract

The database is private (`infra/operations/render-database.yaml` has
`ipAllowList: []`). All database work runs inside Render one-off jobs. The
GitHub runner receives no database connection or database credential.

`jobs` must define `preflight`, `backup`, `worker_gate`, `postflight`, `smoke`,
`cleanup`, `final`, and the selected migration key when one is needed. Each
entry contains `service_id`, `command`, and `review_ref`. A migration also needs
`forward_only: true`. The dispatch input selects a reviewed catalog key; it is
never interpreted as a shell command or an arbitrary existing job to rerun.
The returned Render job ID is a separate identity and is recorded immediately.

Commands are operator-reviewed settings for the qualified service/image; they
must implement the assertions listed in `requiredChecks` in `workflow.mjs`.
Preflight verifies ready state, runtime grants, recovery hold, migration
checksums, reviewed changes and baseline counts. Backup verifies fresh durable
encrypted output and its checksum. Migration verifies forward-only execution,
runtime/backup grants, new objects and unchanged counts. Worker gating proves
the new heartbeat, old-instance drain and empty scoped probe. Postflight proves
public/security/redirect/health/asset checks. Smoke proves the complete synthetic
owner flow. Cleanup removes its rows. Final checks counts, rows, probes, blocks
and failed jobs since release start. Commands must fail rather than emit success
when any assertion is unknown. A `true` placeholder command cannot pass.
Inside the reviewed postflight command, a failed read during proven instance
rollover is repeated once and both observations are retained, as WF-06 step 9
requires. This is not a retry of the one-off job-creation request.

The orchestrator supplies `JITM_RELEASE_CONTEXT` as base64 JSON. It contains the
operation and candidate identities, previous SHA, candidate binding, release
start timestamp, baseline count digest, receipt prefix and required checks.
No credential is in this context. A successful job emits exactly one log line:

```text
JITM_RELEASE_RECEIPT:{"operation_id":"<from context>","candidate_sha":"<from context>","checks":{"<each required assertion>":true}}
```

Preflight adds `counts_sha256`; migration and final add the identical digest of
the same canonical count set. Backup adds `backup_sha256` for its encrypted
object. Store private backup locations and detailed evidence in the operator's
private evidence store. Only allowlisted boolean assertions and digests enter
the public ledger; full logs and arbitrary receipt fields do not.

**NOT RUN / rehearsal h:** the returned one-off job ID, terminal status shape,
log-resource filter, single-receipt delivery, and each reviewed command's actual
assertions have not been verified against Render. The implementation requests
`POST services/<service>/jobs`, records `id`, observes
`GET services/<service>/jobs/<id>`, then reads `/logs` for that job resource.
Missing IDs, missing receipts, missing checks and unknown statuses stop the
release and leave a hold. Qualify these contracts and the settings' command
catalog during h before enabling go-live; do not treat this build as evidence
that a command catalog is installed on the production services.

## Ledger recovery

Every external operation appends `requested` before the request, then persists
its returned ID as `unresolved` before observing it. Missing IDs are represented
by null and evidence “none returned.” A lost runner leaves either `requested`
or `unresolved`, both of which block the next operation/run. There are no
automatic POST retries or time-window resolutions.

The optional dispatch input `ledger_resolution` names exactly one outstanding
`operation_id` and supplies one of:

- E1: `kind`, `operation_id`, `render_deploy_id`, `status`, `observed_status` and
  `reference`. `kind` is `E1`; the two statuses are the same terminal value
  (`succeeded`, `failed` or `cancelled`). The workflow re-observes the **recorded
  returned ID** and checks the deploy candidate. An ID guessed after a lost
  response cannot resolve it. The observed API path replaces `reference`.
- E3: `kind: "E3"`, `operation_id`, `author: "Kevin"`, `decision_ref`, `decision`
  and terminal `status`. Kevin's recorded decision and the exact input digest
  must be included in the approval record. E3 is the route for a missing-ID
  ambiguity, subject to his decision; the code does not infer that decision.

E2 elapsed-time evidence is informational only. Resolution appends history; it
does not erase a request, change a returned ID, or resume a failed step midway.
A fresh attempt performs the full preflight again. If services are partially
deployed, that preflight stops for explicit recovery. No recovery workflow is
implemented in this build.

## Permissions and publication

| Job | Repository permission | Environment / secrets | Executable source |
|---|---|---|---|
| Default | None | None | None |
| `verify` | `contents: read` | No environment, no production secrets | Candidate; full existing CI tier with synthetic fixtures |
| `release` | `contents: write` for the ledger | Production gate; `RENDER_API_KEY` | Owner releaser tag; candidate blobs read as data only |
| `publish` | `contents: write` | No environment secrets | Owner releaser tag; requires successful release |

Publication creates an annotated production tag, then a record branch with the
JITM-15 record and an owner summary. It never moves an existing tag and never
pushes main. Opening the record PR and updating the feature map are explicitly
manual step 13: `pull-requests: write` is not granted. A partial publication
failure is reconciled manually from its existing tag/branch and ledger; it must
not trigger another deploy. Physical devices and customer outcomes are never
claimed by these jobs.

NOT RUN: environment/ruleset/variable/secret creation, workflow dispatch,
production services, databases, one-off commands, tags, PR creation and go-live.
