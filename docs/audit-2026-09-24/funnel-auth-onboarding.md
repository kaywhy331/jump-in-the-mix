## Findings (ranked, most severe first)

### F1. New accounts default to UTC and onboarding never detects the phone's timezone, so Today, due times and the default follow-up date are computed in the wrong zone
- Severity: P1
- Status: VERIFIED
- Evidence:
  - `src/lib/account-provisioning.ts:42` — every new account is created with `userPreference.timezone = "UTC"` (register, magic-link and OAuth paths all go through `createBusinessAccount`).
  - `src/app/onboarding/page.tsx:17,29` — the onboarding page passes `timezoneForUser(user.id)` → `src/lib/display-preferences.ts:5-13` returns that stored `"UTC"`.
  - `src/components/OnboardingForm.tsx:77` (`<TimezonePicker defaultValue={timezone} onChange=… />`) and `src/components/JourneyPreferenceFields.tsx:18` (mega-mix path) never pass `confirmDetection`; `src/components/TimezonePicker.tsx:15,55-60` only reads `Intl.DateTimeFormat().resolvedOptions().timeZone` when `confirmDetection` is true, and a repo-wide grep finds no caller that sets it. The user sees "Coordinated Universal Time (UTC)" and must tap Change → "Use device timezone" (`TimezonePicker.tsx:64,70`).
  - The chosen zone is persisted as-is by all three finishing paths: `src/lib/onboarding-actions.ts:124` (person path), `:134-147` (Skip for now, keeps the submitted UTC), `src/lib/mega-mix-service.ts:31` (mega-mix install).
  - Consequences: `src/app/(app)/jumps/page.tsx:119-125` builds today's/this week's window from that zone; `src/components/LocalDateInput.tsx:10-13` shows "today" per that zone; the starter's first Beat is scheduled at `sendTimeMinutes` in that zone (`onboarding-actions.ts:96-107,127`); quiet hours (`initialJourneySetup` defaults 20:00–08:00) are interpreted in it.
  - The repo's own e2e test works around this by picking Chicago manually (`e2e/core-flows.spec.ts:152-155`).
- Failure scenario: a Denver plumber accepts an invite at 7 PM MDT on Monday, keeps every default, and taps "Prepare my first follow-up". The date field already shows Tuesday (it is Tuesday in UTC), the Beat lands at 10:00 UTC = 4:00 AM MDT, and from then on Today rolls over to the next day at 6 PM local, so evening reviews show tomorrow's Beats and mark today's as due/overdue; the email digest "hour" and quiet hours are shifted by six hours.
- Fix: (1) In `OnboardingForm.tsx:77` and the onboarding use of `JourneyPreferenceFields` pass `confirmDetection={timezone === "UTC"}` (the picker already detects and shows "Detected automatically for follow-up times."). (2) Better: add a tiny client component to `/register` that fills a hidden `timezone` input from `Intl`, validate with `isValidTimezone` in `registerAction`, and pass it to `createBusinessAccount` (default to "UTC" only when missing); do the same detection on the first `/onboarding` render for magic-link/OAuth accounts. Keep the picker for corrections.
- Effort: S (option 1) / M (option 2); Risk: low; Needs migration: no; Needs owner decision: no
- Tests: Playwright with `timezoneId: "America/Denver"` — a fresh account must see "Denver" pre-selected on `/onboarding` and the welcome Jump must be scheduled on the local date (extend `e2e/core-flows.spec.ts:116`, remove the manual Chicago step); unit test on `createBusinessAccount` that a supplied zone is stored.

### F2. The session cookie is `SameSite=Strict`, but sign-in happens on GET links opened from email and on OAuth callbacks, so the browser may drop the just-created session and land the person on /login
- Severity: P1
- Status: SUSPECTED (code path verified end to end; the browser rule is RFC 6265bis behaviour and was not reproduced here)
- Evidence:
  - `src/lib/auth.ts:80-86` — `store.set(env.cookieName, token, { sameSite: "strict", … })`; `tests/auth-boundary.test.ts:60` pins the string `sameSite: "strict"`.
  - Sessions are created inside requests that arrive as cross-site navigations: `src/app/api/auth/verify-email/route.ts:55-62` (then 302 to `/onboarding?verified=1`), `src/app/api/auth/magic/route.ts:31-32`, `src/app/api/auth/oauth/google/callback/route.ts:10-11`, `src/app/api/auth/oauth/apple/callback/route.ts:17-18` (Apple posts from `appleid.apple.com`, allowed at `src/proxy.ts:48-52`).
  - A Strict cookie is not sent on a navigation whose initiator is another site, and that includes the same-origin redirect hops that follow it. `requireSession` (`src/lib/auth.ts:204-210`) then redirects to `/login`; `customerReturnPath` (`src/lib/customer-return-path.ts:4`) does not allow `/onboarding`, so `next` is lost too.
- Failure scenario: a realtor on a laptop opens the verification email in Gmail-in-the-browser and clicks "Verify email". The database marks her verified and the cookie is set, but `/onboarding` is requested without it, so she sees the plain login page with no "verified" message; clicking the email link again yields "That verification link is invalid or expired." Same for the magic link (15-minute, single-use), and for "Continue with Google" on a laptop: the callback sets the cookie, redirects to `/jumps`, and the person is bounced back to `/login` as if nothing happened (until they type the URL by hand). Phone mail apps that hand off to the system browser are usually treated as same-site and are not affected, which is why this can look intermittent.
- Fix: either (a) change `auth.ts:82` to `sameSite: "lax"` — every state change is a POST Server Action or route handler behind the origin check in `src/proxy.ts:43-66`, and Lax still withholds the cookie on cross-site POSTs; update `tests/auth-boundary.test.ts:60`; or (b) keep Strict and make the session-creating request same-site: land verify/magic/OAuth on a same-origin page with one button that POSTs (the pattern already used by `/waitlist/confirm`, `src/app/waitlist/confirm/page.tsx:12`). (b) also fixes F5. Either way, after `/api/auth/verify-email` succeeds redirect through `/login?verified=1` when no session cookie is presented.
- Effort: S (a) / M (b); Risk: low (a) medium (b); Needs migration: no; Needs owner decision: yes (documented security posture)
- Tests: Playwright: open the verification/magic URL from a page on a different origin (`page.goto` of a data: or second-origin page, then click a link) and assert the landing is `/onboarding`/`/jumps`, not `/login`; keep the existing CSRF tests.

### F5. Verification and magic-link tokens are consumed by a plain GET, so link scanners can burn them, and a consumed verification link is reported as an error even though the person is now verified
- Severity: P2
- Status: SUSPECTED for the scanner trigger; VERIFIED for the code and the misleading message
- Evidence: `src/app/api/auth/verify-email/route.ts:13-54` consumes on GET and, when the token is already used, redirects to `?error=That verification link is invalid or expired.` without checking that `emailVerifiedAt` is already set; `src/app/api/auth/magic/route.ts:10-32` likewise consumes on GET. The waitlist confirmation deliberately uses a POST button instead (`src/app/waitlist/confirm/page.tsx:12`), so the two flows are inconsistent.
- Failure scenario: a business Microsoft 365 mailbox with Safe Links pre-fetches the verification URL; the user's tap then shows "invalid or expired" and they request another link, which is burned the same way; the account is verified all along and would sign in with the password, but nothing says so. This is the same change as F2 option (b).
- Effort: S–M; Risk: low; Needs migration: no; Needs owner decision: no
- Tests: route tests that GET no longer mutates; a second GET of a used verify token lands on `/login?verified=1`.

### F6. Registration rate limit counts invalid attempts and the lock message reads "about 1440 minutes" (deep-gap "Registration details", still open)

### F7. Sessions expire 14 days after sign-in with no sliding renewal, so a phone-first daily tool signs its user out every two weeks
- Severity: P2
- Status: VERIFIED

## Checked and fine

- Invitation gate cannot be bypassed: every account-creating path (`registerAction`, magic link, OAuth) goes through `claimAccessInvite`, which requires a valid token outside pilot mode (`account-provisioning.ts:10`, `referral-access.ts:78-88`).
- OAuth security: PKCE S256, nonce and single-use state stored server-side, `email_verified` required, issuer/audience checked (`social-auth.ts:43-93,128-140`); Apple `form_post` explicitly allowed by the CSRF check (`proxy.ts:48-52`).
- Enumeration: resend-verification, password reset, magic link and waitlist all return the same receipt whether or not the address exists (`auth-actions.ts:164-170,215-219,247-251`, `waitlist-actions.ts:30-31`); only registration says "already exists", and that message appears inline on `/register`, which already carries a "Sign in" link (`register/page.tsx:48`), so the prior audit's "no link to sign-in" is effectively covered.
- Magic link is issued only for existing accounts (or the first pilot owner) and also verifies an unverified account (`auth-actions.ts:163-170`, `magic/route.ts:28`).
- Password reset is single-use, signs out all sessions and sends a changed-password notice (`auth-actions.ts:266-287`).
- Verification email TTL 24 h, reset 60 min, magic 15 min, OAuth state 10 min (`env.ts:66-68`, `auth-actions.ts:172`).
