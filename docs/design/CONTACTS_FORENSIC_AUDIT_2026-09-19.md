# Contacts forensic audit — jumpinthemix.com

**The Contacts implementation running on the customer site does not match the supplied design.** It retains the previous directory and profile structure beneath the new colors and fonts. The subsequent local correction adds the desktop workspace and compact rows, but still has substantial composition and interaction gaps. It is not ready for visual acceptance as-is.

This is an analysis, not an implementation or deployment. No application code, production records or original design files were changed during this audit.

The style entry point imports 28 stylesheets, including several generations of Contacts, desktop and mobile rules before the design overrides. Importing new rules last is insufficient when an earlier selector is more specific or the DOM structure remains unchanged. Corrections should establish one clear owner for each Contacts component instead of adding another layer of compensating selectors.

**Design/function decisions to settle**

These decisions affect behavior; the clear layout corrections above do not need to wait for them.

1. **What does the Journey line mean?** The reference combines actual dated stage moves, future stages and touchpoints. Stage history can revisit or skip stages. Define how that history is represented and distinguish recorded facts from possible future stages. Do not fabricate expected transition dates.
2. **Which sequence does Next summarize when several Mixes are active?** The reference shows a particular Beat within one sequence. The current local dots combine pending follow-ups from all Mixes. Choose the earliest due item, then show its own sequence context; unrelated upcoming items could remain in Coming up. This is a proposed contract, not existing behavior.
3. **What starts a touchpoint?** The app currently has independent Mix assignment and one-time follow-up workflows. Decide which existing choice “Start a touchpoint” exposes and what confirmation is needed. A new inactive-days automation must not be inferred from the mockup.
4. **How should notes and extra controls fit?** A persistent contact note and a dated activity note are distinct existing records. Keep those meanings clear instead of manufacturing a history date for the persistent note. Place Ask for a review, archive, bulk selection, custom fields and preferences in deliberate secondary controls while retaining access to their current workflows.

**Verification and correction order**

Twelve current local states returned HTTP 200 with no recorded page errors, no horizontal document overflow and no axe WCAG A/AA violations. Read-only interaction checks confirmed Note opens and focuses the composer, and documented sorting's selection reset, stage disclosure depth and the actual review target. Changing the permission filter correctly submitted the live form and updated the directory URL; absence of an explicit submit button is not a defect. All six comparison-viewer states loaded their three images, and all 24 local report links resolve.

These checks do not constitute visual acceptance, a new authenticated production test, an exhaustive keyboard audit, or regression coverage of archive/send/move mutations. No new build was necessary for this analysis-only pass. Fixture names, record counts, timestamps, the real logo and the export's device safe area are not counted as mismatches. Screenshot positions are measurements of the documented fixtures, not mandatory fixed heights for arbitrary customer data.

The correction order should be: **desktop workspace and selection context → compact directory header/rows → phone identity/actions/details/history order → Beat and Journey data semantics → history typography and component styling → direct visual and keyboard acceptance at the supplied widths in both themes**. Intermediate and ultrawide layouts should then be checked for readable reflow. A test-site deployment should follow verified implementation; this audit does not approve the current local version for customer-site publication.
