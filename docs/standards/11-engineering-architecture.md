# JITM-11 — Engineering architecture

> How Jump in the Mix is built: the framework rule, where code lives, the tenant boundary, time and scheduling, the worker, data and migrations, security, and dependencies.

## 1. Purpose and scope

This standard governs application code, the Prisma schema and migrations, the worker, operational scripts and dependencies. It covers the engineering side of the principles in JITM-00 §2: tenant isolation, settled work, the deliberate strengths and cost discipline.

Neighboring topics live elsewhere:
- tests, checks and evidence labels: JITM-12;
- releases, environments and production operations: JITM-14;
- CSS architecture and tokens: JITM-06;
- customer vocabulary: JITM-05;
- feature behavior and workflows: JITM-09.

## 2. Rules

### Framework and runtime

**2.1** Before writing or changing code that uses Next.js, agents MUST read the relevant guide in `node_modules/next/dist/docs/` and follow its deprecation notices. The project runs Next.js 16, whose APIs, conventions and file structure differ from older versions. [SOURCE AGENTS.md:5] [SHIPPED 9439fd6 package.json:88]

**2.2** The Next.js agent-rules block at the top of `AGENTS.md` is written by `next dev` from the installed package. Agents MUST NOT edit its text. Its placement is covered by JITM-16 §2, and committing it by JITM-13 §2.10. [SOURCE AGENTS.md:1-9]

**2.3** Request-level logic lives in `src/proxy.ts`: origin checks, security headers, the CSP nonce and support-view limits. Next.js 16 renamed middleware to proxy, so agents MUST NOT add a `src/middleware.ts`. [SHIPPED 9439fd6 src/proxy.ts:108,185] [SOURCE node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/middleware.md:11 (installed next@16.3.4)]

**2.4** New code in `src/` MUST be TypeScript, checked under `strict` with `allowJs: false`. The JavaScript modules (`scripts/*.mjs` and the two `src/lib/recovery-hold-*.mjs` modules the scripts share) get only syntax and import checks, so a change to one MUST be exercised by running it or its test. [SHIPPED 9439fd6 tsconfig.json:9-11] [SOURCE docs/audit-2026-09-24/tests-quality-process.md:98-99]

**2.5** The web service runs the standalone build, and the worker is a separate long-running Node process at the same commit. Code MUST NOT assume that web and worker share a process or memory, or that a web instance is always running. [SHIPPED 9439fd6 next.config.ts:21] [SHIPPED 9439fd6 render.yaml:44,76] [SOURCE docs/BETA_READINESS_AUDIT_2026-09-26.md:251]

### Where code lives

**2.6** New code goes where its kind already lives:
- `src/app/`: routes. Public pages at the top level, the customer workspace in `(app)/`, staff pages in `(staff)/`, HTTP endpoints in `api/`;
- `src/lib/`: services, Server Actions, repositories and schedulers, as flat modules;
- `src/components/`: React components; `src/styles/`: per-area CSS (JITM-06 §2);
- `src/worker/index.ts`: the only worker entry;
- `prisma/`: the schema split into `*.prisma` files, `prisma/migrations/` and `prisma/seed.ts`;
- `scripts/`: operational tools; `infra/operations/`: database, backup and monitor definitions;
- `tests/`, `e2e/` and colocated `*.test.ts(x)` files: tests (JITM-12 §2).

**2.7** `src/generated/` holds the Prisma client and the schema-release manifest. It is build output, regenerated by `npm run db:generate` and the build, and agents MUST NOT edit it. [SHIPPED 9439fd6 .gitignore:5,42] [SOURCE docs/DATABASE_RELEASE_CHECKS.md:7]

**2.8** `src/lib/actions.ts` MUST stay a re-export-only barrel. Implementations go in scoped modules, and `npm run validate:imports` fails otherwise. [SHIPPED 9439fd6 scripts/validate-imports.mjs:39-50]

### Tenant boundary

**2.9** `workspaceId` MUST come only from the authenticated session, through `requireWorkspace()` or `requireWritableWorkspace()`. It is never read from form fields, query strings, headers or request bodies. [SHIPPED 9439fd6 src/lib/auth.ts:243-260] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:91] [SOURCE CONTRIBUTING.md:57]

**2.10** Every read or write of tenant data MUST be scoped by that `workspaceId`: in routes, actions, worker jobs, imports, exports, notifications and support views. Record lookups use the helpers in `src/lib/workspace-repository.ts` or put `workspaceId` in the `where` clause. [SHIPPED 9439fd6 src/lib/workspace-repository.ts:12-30] [SOURCE docs/SECURITY.md:21]

**2.11** Actions that change data MUST call `requireWritableWorkspace()`, which refuses during a staff support view. [SHIPPED 9439fd6 src/lib/writable-workspace.ts:22-30]

**2.12** Staff pages and actions MUST call `requirePlatformAdmin()` with the permission they need. It reads the person's permissions on every request and requires MFA in production. A layout check alone is never enough. [SHIPPED 9439fd6 src/lib/auth.ts:262-287] [SHIPPED 9439fd6 render.yaml:18-19] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:16]

**2.13** Staff reach a customer's workspace only through the support-case path: an assigned active case, a separate permission, and a timed, read-only view bound to the handler's session, with private reads audited. No other code path may show customer data to staff. [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:16] [SOURCE docs/SECURITY.md:23]

### Time and scheduling

**2.14** A follow-up's time is a logical local date plus minutes after midnight (0–1439) in the workspace's IANA timezone. The UTC instant is derived with `zonedDateTimeToUtc()`, which corrects for daylight-saving changes. February 29 becomes February 28 in other years, days 29–31 clamp to the month's end, and quiet hours, weekend rules and snooze use the owner's timezone. Code MUST NOT schedule from a host-local `Date` or a fixed offset. [SHIPPED 9439fd6 src/lib/jump-schedule.ts:73-75,161-183] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:99,101]

**2.15** Servers and containers run in UTC. Dates shown to a person MUST use the account's saved locale and timezone, never the host's. [SHIPPED 9439fd6 Dockerfile:6] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:99] [SOURCE docs/JOURNEY_PRODUCTION_RELEASE_2026-09-21.md:32]

**2.16** Scheduling writes MUST be idempotent. Each generated follow-up has a deterministic key from `createJumpUniquenessKey()` (workspace, contact, Mix, Beat, occurrence, local date-time and timezone), so a retry or a second pass creates nothing new. [SHIPPED 9439fd6 src/lib/jump-schedule.ts:192-204] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:103]

**2.17** An occurrence with a DONE or SKIPPED row is settled, and no timing, rule or settings change may re-create it. Generated follow-ups record their occurrence; older rows match by their original local date. [SHIPPED 9439fd6 src/lib/jump-engine.ts:329-342] [SOURCE docs/BETA_BLOCKERS_RELEASE_2026-09-26.md:8,25]

**2.18** One-time follow-ups (a promised next follow-up, a reschedule, "Save & schedule" without a Mix, and Quick Add) MUST go through `createOneTimeFollowUp()` in `src/lib/one-time-follow-up.ts`. It creates exactly one follow-up at the chosen time, outside every Mix, which no settings change moves. [SHIPPED 9439fd6 src/lib/one-time-follow-up.ts:26-31] [SOURCE docs/BETA_BLOCKERS_RELEASE_2026-09-26.md:7,24]

**2.19** The rule for when a follow-up may send automatically (review window, quiet hours, working hours, appointments) lives only in `src/lib/automatic-delivery-window.ts`. The worker, Today and the settings preview MUST read it and keep no copy of their own. [SHIPPED 9439fd6 src/lib/automatic-delivery-window.ts:5-9] [SOURCE docs/AUDIT_RELEASE_A2_2026-09-25.md:31]

### Worker and jobs

**2.20** Exactly one worker runs. Background work MUST go through the job table and the claim path in `src/worker/index.ts`: a 10-minute lease (`lockedAt`, `lockedBy`), renewed every 30 seconds and reclaimable once it expires. Agents MUST NOT add a second queue or claim mechanism, and running more workers needs proof that leases hold under load. [SHIPPED 9439fd6 src/worker/index.ts:26-31,123-134] [SOURCE docs/HOSTED_DEPLOYMENT.md:61]

**2.21** Worker passes MUST be bounded: a capped batch per pass (for example 25 workspaces per reconciliation pass, imports in 25-row chunks), with long jobs checking `shouldStop()` between saved steps. [SHIPPED 9439fd6 src/worker/index.ts:55-57,308] [SOURCE docs/HOSTED_DEPLOYMENT.md:68] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:103]

**2.22** On SIGTERM the worker takes no new job, finishes or pauses the job in hand at a saved step, returns the attempt and records a STOPPED heartbeat. New long jobs MUST keep that contract. The worker starts with `node --import tsx src/worker/index.ts` so the signal reaches Node. [SHIPPED 9439fd6 src/worker/index.ts:44-57,393,434-436] [SHIPPED 9439fd6 render.yaml:76-77]

**2.23** Only jobs that reached a recorded failed state are retried. An uncertain provider response is never retried automatically, and durable claims prevent a second send. Idempotency is no reason to ignore unexplained repetition. [SOURCE docs/OPERATIONS_READINESS.md:64] [SOURCE docs/SECURITY.md:35] [SOURCE docs/FULL_AUDIT_2026-09-24.md:139]

**2.24** A user action that can be retried MUST carry one request id per logical attempt, minted once and kept across retries (Quick Add, outcomes, contact create per opened form). A save that could overwrite another device's change MUST be refused, by a fingerprint checked under a row lock or a re-read `updatedAt`, and keep the person's typed entries. [SOURCE docs/design/SAVE_RECOVERY_RELEASE_2026-09-20.md:8] [SOURCE docs/FULL_AUDIT_2026-09-24.md:78] [SOURCE docs/AUDIT_RELEASE_A2_2026-09-25.md:32-33,44]

**2.25** Code that takes more than one lock MUST take them in this order: staff lock, access lock, workspace import key, job rows, batch rows. [SOURCE docs/AUDIT_RELEASE_C1_2026-09-25.md:30]

### Data model and migrations

**2.26** Schema changes MUST be made in the `prisma/*.prisma` files with a generated migration in `prisma/migrations/<YYYYMMDDHHMMSS>_<snake_case>/`, reviewed line by line before it is committed. [SOURCE CONTRIBUTING.md:48-49] [SHIPPED 9439fd6 prisma.config.ts:5-8]

**2.27** Migrations are append-only history. Agents MUST NOT edit, rename or delete a migration once it has been applied to a shared database, and MUST NOT change migration history, checksums or the release manifest to make a check pass. A mismatch gets a corrective migration. [SOURCE docs/MIGRATION_RUNBOOK.md:3] [SOURCE docs/DATABASE_RELEASE_CHECKS.md:28,38]

**2.28** Migrations SHOULD be additive (new tables, nullable or defaulted columns) so the previous release keeps running on the migrated schema. Additive is not automatically safe to roll back, so the rollback plan (JITM-13 §2.15) and the rollback rules (JITM-14 §2.24) still apply. [SOURCE docs/AUDIT_RELEASE_B_2026-09-25.md:14] [SOURCE docs/PR78_PRODUCTION_PROMOTION_DECISION_2026-09-16.md:48]

**2.29** A destructive migration (dropping a table, column or index, or rewriting data) needs Kevin's approval, a fresh backup and a maintenance window. [SOURCE docs/DATABASE_RELEASE_CHECKS.md:15] [SOURCE docs/DATABASE_HAND_WRITTEN_OBJECTS.md:46] [PROPOSED]

**2.30** Hand-written database objects (partial and trigram indexes, CHECK constraints, triggers) live only in migrations and are listed in `docs/DATABASE_HAND_WRITTEN_OBJECTS.md`.
- Agents MUST NOT accept a generated `DROP INDEX` for them.
- A new one goes in a migration, on that list, and in the residue test's reviewed list.
- Every foreign key a migration creates MUST have a Prisma relation.

[SOURCE docs/DATABASE_HAND_WRITTEN_OBJECTS.md:3,5,14,17]

**2.31** Any database other than a throwaway local one MUST be built with `prisma migrate deploy`. `prisma db push` omits the hand-written objects. [SOURCE docs/DATABASE_HAND_WRITTEN_OBJECTS.md:9-12]

**2.32** Each build carries a generated schema-release manifest, and code serves only when `npm run db:verify-release` passes against its database. [SOURCE docs/DATABASE_RELEASE_CHECKS.md:3,7,9] [SHIPPED 9439fd6 render.yaml:43]

**2.33** The web service and worker connect as the restricted `jitm_runtime` role. The owner credential appears only in the isolated migration job (`scripts/migrate-with-owner.mjs`), never in application code, service environments or the pre-deploy command. The migration step MUST confirm the backup role can read new or altered tables. [SOURCE docs/RUNTIME_DATABASE_CREDENTIALS.md:3-5,19-21] [SHIPPED 9439fd6 render.yaml:1-3,43] [SOURCE docs/AUDIT_RELEASE_B_2026-09-25.md:85]

**2.34** Completed history and rendered messages are immutable; editing business details refreshes only still-pending messages. Published library and System Mix revisions cannot be updated. Deliveries, notifications, review requests, actions and staff access leave auditable receipts. [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:95,105,111] [SOURCE docs/DATABASE_HAND_WRITTEN_OBJECTS.md:52-57]

**2.35** Contact methods are compared by a stable normalized identity, never raw input. Phone numbers use the international-form key from `src/lib/phone-number.ts`, and every matcher also accepts the older digits key. [SHIPPED 9439fd6 src/lib/phone-number.ts:6-20] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:95]

### Security

**2.36** Session handling stays as shipped unless Kevin approves a change:
- tokens are random and stored only as SHA-256 hashes;
- the cookie is HttpOnly, `SameSite=Lax`, and Secure on public origins;
- the browser keeps it for the absolute cap (`AUTH_SESSION_MAX_DAYS`, default 90, at most 400 days);
- the session row slides on the idle window (`AUTH_SESSION_DAYS`, default 14).

[SHIPPED 9439fd6 src/lib/auth.ts:23,43,96-105] [SHIPPED 9439fd6 src/lib/env.ts:59-61,157-158] [SOURCE docs/FULL_AUDIT_2026-09-24.md:137]

**2.37** Tokens in links and callbacks (magic links, OAuth state, access grants, review and referral links) MUST be random and expiring, and single-use where the flow allows. OAuth state is stored only as a hash. [SOURCE docs/SECURITY.md:5,37] [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:12]

**2.38** Unsafe requests MUST pass the origin check in `src/proxy.ts`. Server Actions share the `AUTH_ALLOWED_ORIGINS` allowlist and a 1 MB body limit. The Apple sign-in callback and signed webhooks are the only exceptions. [SHIPPED 9439fd6 src/proxy.ts:143-148] [SHIPPED 9439fd6 next.config.ts:34-38] [SOURCE docs/SECURITY.md:13]

**2.39** Every response carries a fresh nonce-based Content Security Policy (`strict-dynamic`, with `unsafe-eval` only outside production) and the headers set in `src/proxy.ts`. Inline scripts MUST carry the request's `x-nonce`, as the root layout does. Agents MUST NOT add `unsafe-inline` or third-party script hosts. [SHIPPED 9439fd6 src/proxy.ts:74-77,93-104] [SHIPPED 9439fd6 src/app/layout.tsx:40-46]

**2.40** Client IP addresses MUST come from `src/lib/client-ip.ts`, which walks forwarded hops from the right past trusted proxies (private networks, Cloudflare, `TRUSTED_PROXY_CIDRS`). Code MUST NOT trust the first `X-Forwarded-For` hop. [SHIPPED 9439fd6 src/lib/client-ip.ts:3-11] [SOURCE AGENTS.md:17] [SOURCE docs/FULL_AUDIT_2026-09-24.md:146]

**2.41** Secrets stay out of code and the repository:
- agents MUST NOT commit `.env` files, provider secrets, tokens or customer exports;
- credentials stay server-side, and provider keys never reach the browser;
- `DATA_ENCRYPTION_KEY` is unique per environment, kept in the host's secret manager, separate from the backup key, and never rotated without a re-encryption plan.

[SOURCE CONTRIBUTING.md:55-56] [SOURCE docs/SECURITY.md:27,39] [SOURCE docs/EMAIL_OPERATIONS.md:113]

**2.42** Logs, errors and diagnostics MUST NOT contain passwords, tokens, MFA material, OAuth codes, provider credentials, keys, exports, message bodies or notes. Database URLs are redacted. [SOURCE docs/SECURITY.md:29] [SOURCE docs/MIGRATION_RUNBOOK.md:57]

**2.43** Webhooks verify the signature against the raw request bytes, bound the body size, deduplicate event ids and stay idempotent. [SOURCE CONTRIBUTING.md:58] [SOURCE docs/EMAIL_OPERATIONS.md:16]

**2.44** Error text reaches a page only as fixed wording. Services throw `UserFacingError` for messages meant for people, anything else becomes the page's fixed sentence, and `?error=` text shows only when our code signed it. [SHIPPED 9439fd6 src/lib/user-facing-error.ts:1-10] [SOURCE docs/AUDIT_RELEASE_B11_2026-09-25.md:18-21]

**2.45** Reports and analytics hold aggregate counts only, with no customer content or identities, and use no paid analytics service. Report exports are encrypted, bound to the staff session and expire. [SOURCE docs/CANONICAL_PRODUCT_DECISIONS.md:154,156] [OWNER 2026-09-25 O4] [PROPOSED]

**2.46** A change that edits many records at once from a generated suggestion MUST ask the person to confirm first. [SOURCE CONTRIBUTING.md:59]

### Billing

**2.53** Billing stays off unless `BILLING_ENABLED` is true and both Stripe secrets are set. While it is off, nothing can be bought, no plan limits apply and the Stripe webhook refuses events. Readiness refuses a partial billing configuration, and a test key in hosted production. [OWNER 2026-09-29 docs/PRICING_DECISION_2026-09-29.md:12] [PROPOSED]

**2.54** An account's plan changes only from Stripe's own record. Webhook events are verified against the raw request body and the endpoint's signing secret, and recorded once by event id; each one re-reads the customer's subscriptions, so late, repeated or out-of-order events leave the right plan. A return from checkout is confirmed with Stripe before the page shows the plan; the return address never grants one. [SOURCE docs/PRODUCTION_LAUNCH_PLAN.md:96] [PROPOSED]

**2.55** Card details never reach the app: buying, card and plan changes and cancellation happen on Stripe's hosted checkout and billing portal. Only the account owner, outside a support view, can open them, and an account holds at most one paid plan. [SOURCE docs/PRODUCTION_LAUNCH_PLAN.md:23,90] [PROPOSED]

**2.56** Prices come from `src/lib/plans.ts`. A Stripe price is sold only when its lookup key, amount, currency and interval match the plan exactly, so a price edited in Stripe can't be charged; a changed price needs a new lookup key and a code change. [OWNER 2026-09-29 docs/PRICING_DECISION_2026-09-29.md:11] [PROPOSED]

**2.57** Deleting an account first deletes the Stripe customer of every workspace the person owns (the workspaces the deletion removes), which ends every subscription; it never touches a workspace they only belong to. A refusal the person can act on (the last active staff owner) is checked before any customer is deleted; if Stripe fails, nothing is deleted. [PROPOSED]

**2.58** Plan limits are enforced in `src/lib/plan-limits.ts` and only while billing is on (§2.53). People: the workspace's `PlanPerson` rows are the people with follow-ups on. Before every follow-up generation pass, the worker settles them for the whole workspace under the workspace's own advisory lock: a person with no running Mix leaves, someone new joins while there is room (earliest enrollment first), and anyone left over gets a `MixStop` with reason `plan.limit` in each Mix that would have started for them. While billing is off everyone is counted, so the people an account has when charging starts keep their follow-ups. A start the owner makes directly (a contact's Mix, a workflow start, a new contact's first Mix, a visit's plan, Resume) reserves the place first and is refused when there is none, taking the plan's lock before any contact row lock. Active Mixes: every path that turns a Mix on checks the count inside its transaction; a Mega-Mix counts as one, and `ONE_TIME` and `STARTER` Mixes don't count. [OWNER 2026-09-30 docs/PLAN_LIMITS_IMPLEMENTATION_2026-10-01.md:8] [OWNER 2026-09-30 docs/PLAN_LIMITS_IMPLEMENTATION_2026-10-01.md:9] [PROPOSED]

### What stays deliberately strong

**2.47** These controls MUST NOT be weakened, bypassed or disabled to pass a check, simplify code or speed a release. They add engineering detail to JITM-00 §2.
- The recovery hold and its fail-closed deadlines (read 7 s, outer check 8 s, connect 5 s, query 2 s, statement 1.5 s).
- The release-compatibility check: there is no production bypass flag, and `CI=true` disables nothing.
- The `jitm_runtime` role boundary.
- TLS verification, origin checks, the CSP, security headers and support-view limits.
- Job leases, the SIGTERM stop, crash-safe imports, and a service worker that never caches HTML.

## 4. Do / Don't

- **Do** read `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md` before touching `src/proxy.ts`. In a new worktree, run `npm ci` first so the docs exist.
- **Do** look records up with the scoped helpers, for example `findWorkspaceContact(db, workspaceId, contactId)`, not a lookup by `id` alone.
- **Do** compute a send time with `zonedDateTimeToUtc(logicalDate, minutes, timezone)`.
